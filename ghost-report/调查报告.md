# Tauri 桌宠透明重影调查（未完成 Tauri 闭环）

日期：2026-11-10。所有证据位于本目录。结论依据本次实测，不沿用此前机器状态。

## 结论与边界

原版 Tauri 的拖动叠影根因尚未查定，没有可宣称已在 Tauri 验证有效的修法。当前环境阻止了必要的复现—修复—回归闭环。

已独立复现一类相符症状：最小 WebKitGTK 4.1 的 canvas 气泡像素已经变成 alpha=0，spectacle 合成截图仍显示原来的色块。GTK/cairo 和 Qt/QPainter 对照没有此残留。它将调查范围缩小到 WebKit 参与的透明输出链，但不能单凭这些结果把责任定位到 WebKit 的某个缓存、GTK 的子窗口、KWin 或 NVIDIA，也不能证明气泡残留与原版拖动叠影同源。

## 环境与阻塞

- `环境.log`：KWin 5.24.7、X11、Qt 5.15.3，合成启用，NVIDIA RTX 4090 D、580.178.04、OpenGL/GLX；DP-0 位于 (0,2160)，3840×2160。
- pkg-config 查询：GTK 3.24.33、WebKitGTK 4.1 库 2.50.4。
- `build.log`：按指定 env.sh 和 target-ghost 构建立即失败，`Read-only file system (os error 30)`。当前沙箱允许写入的根目录不含 `/mnt/data2`，且禁止提权。未改用系统盘大目录，也未使用主线 target 构建。
- 当前沙箱的 nvidia-smi 无法连接驱动；最小 WebKit 日志明确记录 GTK 无法创建 GL 上下文、自动禁用硬件加速。这不能推出桌面 NVIDIA 驱动失效；KWin 是沙箱外已运行的进程。也不能用此实验代表原版 Tauri 的加速路径。
- 未运行原版 Tauri：其 `cc_state()` 会删除过期会话文件，必须先编译隔离补丁，才能满足不触碰共享会话的约束。

## 方法

固定窗口物理尺寸 200×240，DP-0，初始请求位置 (3000,3800)。素材来自同一 `neutral-N.png`，图像放在 (4,32)。用 XTest 鼠标按下和移动，GTK 调用 begin_move_drag，Qt 调用 startSystemMove，实际交给 KWin 移动。日志记录每次截图时的真实位置和窗口 ID。

每个有效试次独立启动一次，往返拖动 3 次，每次拖后截图 2 次。每次试次用 `flock /tmp/claude-1000/desk-pet-mouse.lock timeout 55 ...` 包住整个运行，结束释放；仅终止自己创建的进程。截图命令均为 `spectacle -b -n -f -o`，保留 `*-full.png`，再以真实窗口坐标裁剪为 `*-crop.png`，不以 ImageMagick root 截图判定。

原生 GTK/Qt 使用固定物理像素绘图，关闭自身自动高 DPI 放大；未改系统缩放。WebKit canvas 的 CSS 铺满视口，底层 200×240，保留系统页面缩放的影响。没有覆盖 Qt6、Qt Quick、跨屏移动、长时间运行或原版动态人物帧。

## 对照结果

|实验|有效重复|结果|证据|
|---|---|---|---|
|最小 GTK3/cairo|2 次启动、6 次拖动、12 张截图|未见多个人影；色块能清除|`gtk-1.log`、`gtk-2.log`、`contact-1.png`、`gtk-2-contact.png`|
|最小 Qt5/PyQt5 QWidget/QPainter|2 次启动、6 次拖动、12 张截图|未见多个人影；色块能清除|`qt-1.log`、`qt-2.log`、`contact-1.png`、`qt-2-contact.png`|
|最小 WebKit4.1，带状态标记|试次 5、6|alpha=0 时仍留洋红色块|`webkit-5-0-1-crop.png`、`webkit-6-0-1-crop.png` 及对应日志|
|WebKit + 父窗口 draw 中 cairo CLEAR|试次 7、8|仍留色块|对应 `webkit-7-*`、`webkit-8-*`|
|WebKit + CLEAR + 移除 will-change:transform|试次 9、10|仍留色块|对应 `webkit-9-*`、`webkit-10-*`|

GTK 第二次启动的实际起点偏离请求位置，但仍在 DP-0，日志显示随后往返移动；没有把请求坐标当成实际坐标裁剪。

WebKit 中每 2 秒切换一次洋红色块。每次绘制先 clearRect，再绘制人物；读 (20,10) 的 alpha，alpha=0 时在左下角画不透明青色标记，否则画红色标记。这样同一张合成截图可以判断前端当前状态，避免靠日志与截图时间猜测。残留色块是 184×22=4048 个洋红像素；状态标记是 10×10=100 个像素。详见 `像素核对.md` 与 `透明残留对照.png`。

试次 1 因缺少 WebKit 4.1 GI typelib 失败；试次 2 改用系统 4.1 C ABI 后运行，但未成功拖动且 CSS 尺寸不匹配，排除出有效对照。试次 3、4 修正了拖动与尺寸，但没有状态标记，仅作预实验保留。C ABI 版本没有换用系统已有的 WebKit4.0 GI 绑定。

## 源码核对与解释

本地依赖 tao 0.37.2 的 linux/window.rs 为透明窗口设置 RGBA visual 与 app_paintable；linux/event_loop.rs 的透明绘制分支本身已有 SOURCE 透明填充，再恢复 OVER。wry 的 webkitgtk/mod.rs 设置 WebView 背景为全透明。因此“只要给父窗口加一次透明 CLEAR”不能直接视为原版缺失的修复；本次最小实验也显示该操作没有清掉色块。

GTK 官方绘制模型说明，app_paintable 会关闭 GtkWindow 默认内容绘制，draw 会沿子控件层级传播，GDK 又有自己的双缓冲。canvas alpha=0 只验证 canvas 的数据，不能验证后续所有层的输出；页面 reload 不销毁整条原生窗口/合成链，也不能单独锁定 KWin。参考：[GTK3 绘制模型](https://docs.gtk.org/gtk3/drawing-model.html)。这些是定位边界，不是对本机具体故障层的证明。

## Qt 主线风险

本次 Qt5 QWidget/QPainter 对照未复现，支持继续验证原生 Qt 绘图方案，但不等于 Qt6 主线绝不受影响。如果未来证据定位到共享的 KWin/NVIDIA 合成层，Qt 仍可能受相同层影响；目前没有证据支持已经发生这种情况。主线应保留合成截图回归：反复拖动、透明区从有内容变为空、实际 1.5 缩放和跨屏移动。此次未修改 KWin、驱动、主线源码、会话目录、Claude 配置或 Telegram 设置。
